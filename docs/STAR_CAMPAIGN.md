# Ethical repository star campaign

The objective is not a large vanity number. It is a growing group of practitioners who understand the project, run it and choose to follow its development.

## Conversion path

```text
Concrete decision demo
        -> repository visit
        -> synthetic local run
        -> useful result or useful critique
        -> voluntary star, issue, discussion or contribution
```

Do not buy stars, trade stars, use engagement pods or automate GitHub accounts. Never make a star a condition for receiving access, support or a feature.

## First 25-user cohort

Recruit five people from each group:

1. Heads of marketing or growth
2. RevOps and marketing-operations practitioners
3. Performance and lifecycle marketers
4. Analytics and data engineers
5. MCP, Claude and Codex builders

Ask for a 20-minute test, not a star. Use this message:

> I built an open-source marketing decision system that connects evidence from analytics, search, ads and CRM to Claude or Codex. Calculations run in code and actions stay human-approved. Would you be willing to run the synthetic demo and tell me where the evidence or workflow breaks? If it proves useful, a GitHub star helps other practitioners discover it.

Track the cohort without storing private correspondence in the repository:

| Stage | Target |
|---|---:|
| Personally invited | 25 |
| Ran the demo | 15 |
| Submitted feedback | 8 |
| Opened an issue or contribution | 4 |
| Voluntarily starred | Measure, do not pressure |

## Seven-day distribution plan

### Day 1: proof

- Record the 60-second demonstration in `docs/DEMO_60_SECOND.md`.
- Publish the repository link as the only primary call to action.
- Pin the demonstration post on the founder's profile.

### Day 2: practitioners

- Share the problem and demonstration in RevGenius.
- Invite the first five RevOps and marketing-operations testers privately.

### Day 3: technical depth

- Publish `docs/COMMUNITY_LAUNCH_ARTICLE.md` on DEV.
- Explain deterministic calculations, provenance and approval boundaries.

### Day 4: open-source contribution

- Share the corpus and connector testing requests with open-source communities.
- Point contributors to labelled, bounded issues.

### Day 5: transparent failure

- Publish one limitation discovered by a tester and the resulting fix or backlog item.
- Invite disagreement instead of claiming the system is complete.

### Day 6: use-case variation

- Demonstrate one SEO, one paid-media or one measurement-quality question.
- Keep the same evidence-tier labels and human-decision boundary.

### Day 7: learning report

- Report runs, feedback themes, defects and merged improvements.
- Thank contributors by name only with their permission.

## Measures that matter

Review weekly:

- Unique repository visitors
- README-to-demo clicks
- Successful synthetic demo runs reported
- Testing issues opened
- Returning contributors
- Stars from identifiable practitioner distribution events

Stars are an outcome of useful discovery. They are not the product goal.
